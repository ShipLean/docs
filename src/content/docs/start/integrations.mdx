Connect GitHub or GitLab to show live pull request, merge request, and issue details on Feature links. Webhooks can add pull or merge request links to Stories, Tasks, Bugs, and Action items automatically. They also complete linked work when all requests are closed and at least one is merged. You can also send application logs to Seq.

## Connect GitHub and GitLab link cards

Set integration defaults in the **Integrations** section of **Instance settings**, or provide the matching environment variables. Settings saved in the app override the environment defaults for the GitHub and GitLab tokens and the GitLab URL. `SHIPLEAN_GITHUB_API_URL` can be set only in the environment. Clearing the saved GitLab URL restores the environment URL and token pair. The environment token is never combined with a saved GitLab URL.

| Setting | What it enables |
| --- | --- |
| `SHIPLEAN_GITHUB_TOKEN` | Lets GitHub Feature links show private issue and pull request details, as well as public ones. Without a token, only public repositories can be read. |
| `SHIPLEAN_GITHUB_API_URL` | GitHub API endpoint. Keep the default `https://api.github.com`, or set a GitHub Enterprise Server API URL such as `https://github.example.com/api/v3`. |
| `SHIPLEAN_GITLAB_URL` | The GitLab host whose Feature issue and merge request links ShipLean reads, such as `https://gitlab.example.com`. Other GitLab hosts remain ordinary links. |
| `SHIPLEAN_GITLAB_TOKEN` | Lets GitLab Feature links show private issue and merge request details on the configured GitLab host. |

Tokens are sent only to HTTPS API addresses. The app does not save a token with an HTTP URL. Store tokens in instance settings or in your secret manager. Give each token only the read access it needs to retrieve issue and request details.

To use environment values only, add these settings to your deployment environment:

```dotenv
SHIPLEAN_GITHUB_TOKEN=<github-read-token>
SHIPLEAN_GITHUB_API_URL=https://api.github.com
SHIPLEAN_GITLAB_URL=https://gitlab.example.com
SHIPLEAN_GITLAB_TOKEN=<gitlab-read-token>
```

Omit the GitLab settings if you do not use GitLab. To use GitHub Enterprise Server, point `SHIPLEAN_GITHUB_API_URL` at its API endpoint. The integration makes API requests only to configured HTTPS hosts.

## Turn on pull request webhooks

Webhooks let GitHub or GitLab tell ShipLean when a request opens, changes, merges, or closes. Each provider has its own secret and endpoint. While a provider's secret is unset, its endpoint returns 404. Set the secret on ShipLean first, then configure the same value in the provider.

Generate a separate long random secret for each provider. For example:

```sh
openssl rand -hex 32
```

Set one or both values in the ShipLean environment:

```dotenv
SHIPLEAN_GITHUB_WEBHOOK_SECRET=<github-webhook-secret>
SHIPLEAN_GITLAB_WEBHOOK_SECRET=<gitlab-webhook-secret>
```

When ShipLean is behind an identity proxy, configure the proxy to skip sign-in for `/api/webhooks/`. The webhook endpoint authenticates deliveries with its provider secret. GitHub must send `Content-Type: application/json`, and GitLab posts JSON. See [sign-in options](/start/sign-in/#keep-the-backend-private) for the proxy path requirements.

### Configure GitHub

On a repository, open **Settings**, select **Webhooks**, and choose **Add webhook**. An organization owner can add an organization webhook under **Organization settings**, then **Webhooks**, then **Add webhook**. The organization webhook covers the organization's repositories. Set:

- **Payload URL:** `https://shiplean.example.com/api/webhooks/github`
- **Content type:** `application/json`
- **Secret:** the value of `SHIPLEAN_GITHUB_WEBHOOK_SECRET`
- **Which events:** select **Let me select individual events**, then **Pull requests** only.
- Make sure the webhook is **Active**, then add it.

GitHub sends a `ping` when you create the webhook. ShipLean responds with `pong`.

### Receive GitHub issues and comments

You can also let ShipLean turn GitHub issues into conversations that propose and track work. Add **Issues** and **Issue comments** to the GitHub webhook's selected events, keeping **Pull requests** enabled. Reuse the GitHub webhook URL and secret above. Then, in the project's settings, enable **Take GitHub issues**. The project needs its GitHub repository, an agent connection, and a **run as** project member whose email is allowed by the configured agent relay. The instance GitHub token must be able to read and write issues and read Actions runs. The relay must be deployed and allow the run-as person's email. The project settings page lists missing configuration; it cannot verify that the relay is ready.

When an issue opens, ShipLean creates a Story or Bug in a Triage state and an agent drafts a proposal from the issue, its comments, repository context, and related work. The issue author or a GitHub maintainer can accept the latest proposal by replying with `LGTM` as the first word. Other replies from them start another proposal round; other commenters' replies are mirrored for the agent. Once accepted, ShipLean moves or creates the proposed work item and posts progress as that work advances. A maintainer can comment `/shiplean` to start or resume a held conversation. The project setting controls proposal instructions and the maximum rounds.

### Configure GitLab

On a project, open **Settings**, select **Webhooks**, and choose **Add new webhook**. A group owner can create a group webhook for the group's projects. Set:

- **URL:** `https://shiplean.example.com/api/webhooks/gitlab`
- **Secret token:** the value of `SHIPLEAN_GITLAB_WEBHOOK_SECRET`
- **Trigger:** **Merge request events** only.

GitLab's current webhook UI offers a signing token as a stronger option than a plain secret token. ShipLean currently verifies the `X-Gitlab-Token` secret-token header, so use the **Secret token** field for this integration. A GitLab signing token is not compatible with this endpoint.

GitLab's menu and fields are documented in [Configure webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/). GitHub's [webhook creation guide](https://docs.github.com/en/webhooks/using-webhooks/creating-webhooks) documents the payload URL, JSON content type, secret, event selection, and ping delivery.

## Link and complete work from requests

Put a work item key in the pull or merge request title, its source branch, or a `ShipLean IDs:` line at the start of its description. Titles must use an uppercase key of two to four letters and digits, such as `SHIP-123`. Branch keys can use any case, such as `feature/ship-123-search`.

To name many items, or the items of a Feature, start the description with a `ShipLean IDs:` line:

```text
ShipLean IDs: SHIP-12, SHIP-13, SHIP-20
```

Only the first non-blank line of the description counts, and it must start with `ShipLean IDs:`. Keys use uppercase letters, and a comma or a space separates them. A key further down the description links nothing. On GitHub this is the pull request description, and on GitLab it is the merge request description.

Stories, Tasks, Bugs, and [Action items](/ui/sprint-retro/#raising-an-action-item) link by their own key. ShipLean skips a key that matches no item, and an Epic's key, without an error. A Feature's key links nothing from the title or branch. In the `ShipLean IDs:` line, a Feature's key links every Story, Bug, and Action item directly under it. ShipLean reads the Feature's children when the event arrives. A merge then completes them, including any that still have open Tasks. ShipLean does not link the Feature or its Tasks.

ShipLean reads at most 100 keys from the line and ignores the rest. One event links at most 100 items. If the named keys and the children of any named Feature come to more, each later event for the request links up to 100 more. The link card shows whether the request is open, merged, or closed. ShipLean does not create work items from webhook payloads.

An item moves to its type's first Completed state when all pull or merge requests linked to it are merged or closed, and at least one has merged. A close without a merge does not complete an item on its own. If an item has several linked requests, one that is still open, or one with no event yet, keeps the item open. Reopening a request updates its card but does not reopen a completed work item.

If someone removes an auto-created link, ShipLean does not add it again. Removing the key from a title later also leaves the existing link in place. You can inspect webhook deliveries in each provider's delivery log.

Each provider's endpoint accepts events from any repository or group that holds the right secret. ShipLean has no repository allowlist. Keep each secret private. To rotate a secret, change the matching environment variable. Each provider can be disabled on its own by unsetting its secret, after which its endpoint returns 404.

## Send logs to Seq

Set `SHIPLEAN_SEQ_URL` to your Seq server's ingestion endpoint. If the Seq instance requires an API key, set `SHIPLEAN_SEQ_API_KEY` as well. ShipLean writes logs to the console and also sends them to Seq.

```dotenv
SHIPLEAN_SEQ_URL=http://seq.example.com:5341
SHIPLEAN_SEQ_API_KEY=<seq-ingestion-key>
```

Use HTTPS when the endpoint is reachable over an untrusted network. Keep the API key in your deployment's secret store.

## Export traces, metrics, and logs

To send telemetry to an OTLP collector, set `OTEL_EXPORTER_OTLP_ENDPOINT`. This enables traces, metrics, and logs. Without it, OTLP export is off. ShipLean keeps logging to the console and, when Seq is configured, to Seq.

```dotenv
OTEL_EXPORTER_OTLP_ENDPOINT=https://otel-collector.example.com
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_EXPORTER_OTLP_HEADERS=api-key=<collector-api-key>
OTEL_SERVICE_NAME=shiplean-production
OTEL_RESOURCE_ATTRIBUTES=deployment.environment=production
```

Set the protocol to the one your collector accepts, either `grpc` or `http/protobuf`. With `http/protobuf`, the exporter adds signal paths such as `/v1/logs`. Put credentials in `OTEL_EXPORTER_OTLP_HEADERS`, and keep them in your deployment's secret store. `OTEL_SERVICE_NAME` defaults to `shiplean`. The resource attributes are optional. For OTLP details, see the [OpenTelemetry .NET configuration reference](https://opentelemetry.io/docs/zero-code/dotnet/configuration/).

For every integration variable and its defaults, see [configuration](/start/configuration/).

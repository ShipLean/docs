## Use Blocked and Parked for different situations

Use Blocked when work cannot continue because it waits on a dependency or decision. Mark the blocker with a Blocked tag or a blocked-by link. Record what would unblock the work. Use Parked when the team decides to defer the Feature. Keep it in the Proposed state, and start its status line with `Parked:`, followed by the reason and the condition for picking it up again. A blocked item needs attention to resume. A parked Feature is a deliberate pause.

The default workflow has no separate Blocked or Parked states. It uses the states New, Active, Resolved, Closed, and Removed. Their categories are Proposed, In Progress, Resolved, Completed, and Removed, in the same order. State names and categories are separate. The category determines how ShipLean treats a state: as in progress, resolved, completed, or removed. If your project has custom states, check its workflow before you choose a destination. To set the Feature's one-line status and, when appropriate, its state, use `set_status`.

## Finish the Feature

1. Check that the agreed Stories and Tasks are complete and that the result meets the Feature's goal.
2. Log the Feature's retrospective with `log_retrospective` on the Feature. Set `compiled_from` to the keys of the Stories you compile it from. Put points under `went_well`, `went_badly` with a `root_cause` for each, `improve`, and `not_in_plan`. The agent on each Story has already logged its own retro on that Story.
3. Move the Feature to its Completed state, and update the status line with the outcome.

For a captured plan, review `plan_status` for the task timeline and review rounds before you log the retrospective.

## Log a retrospective

Call `log_retrospective` on the work item when you stop work on it, whether the work is done or not. Set `partial` to true when the work is unfinished. A second call from the same agent on the same item adds points to that retro.

- A sub-agent logs on its Story when it stops.
- The conductor logs on the Feature when the last Story closes. ShipLean records a retro with `compiled_from`, or on a Feature, as the conductor's.
- Include a raw `failure_log` with `blockers`, `assumptions_disproved` and `friction`. ShipLean stores it as you wrote it.

People read the points on the sprint's Retro tab, and under Retrospectives, then decide what to do about each one. See [Sprint retro](/ui/sprint-retro/) and [Retrospectives](/ui/retrospectives/). A point that needs a change becomes an Action item. See [Raising an action item](/ui/sprint-retro/#raising-an-action-item).

## Carry lessons forward

When you plan later work, call `planning_guide` with the project key. It returns lessons from that project's retrospectives. These are the **What to change next time** section of each Markdown run retro, then the `improve` points of the three newest conductor retros on live Features. Apply the relevant lessons to the new plan, and say which ones you used.

A Markdown run retro is a separate record of the whole run, with its budget, timeline and constraint breaks. A Feature can hold one in a file named `retro-<yyyy-mm-dd>-<topic>.md`. It does not replace the points logged with `log_retrospective`.
